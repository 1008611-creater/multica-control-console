# 模板：问题简报（DEFINE）

## 元数据

- 风险等级：L0；涉及范围、授权或架构边界时升级为 L2/L3
- 责任角色：自媒体主控
- 把关角色：用户本人
- 项目身份：填写不可变 `project_id`；新项目先建立控制台再填写

## 目标

在写规格或计划之前，把「用户是谁、要解决什么问题、明确不做什么」一次说清，作为 DEFINE 阶段的固定产物，避免直接进入实现。

## 输入

- 用户原始目标、问题和已知限制；
- 现有 `PROJECT_CONTEXT.md` 与 `docs/product-spec.md`（如已存在）；
- 相关项目的 `project_state.yaml`。

## 输出

一份问题简报，至少包含：

1. 用户与使用场景；
2. 问题陈述（现状 → 期望）；
3. 目标与非目标；
4. 边界与约束（安全、授权、数据来源）；
5. 成功判据：可测试的验收标准；
6. 失败场景；
7. 待用户确认项。

## 硬约束

- 不猜测用户意图；不确定处写「缺」并列为待确认项；
- 不把解决方案写进问题陈述；
- 不在 DEFINE 阶段写实现代码，也不触发生成、登录或发布；
- 结论必须能追溯到用户原话或仓库内真实文件。

## 验收

- [ ] 用户、问题、目标、非目标四要素齐全；
- [ ] 至少三条可测试的成功判据；
- [ ] 明确写出不做什么；
- [ ] 待用户确认项单独列出，未确认前不进入 PLAN。

## 失败处理

用户、边界或成功判据缺失时，任务进入 `blocked`，列出缺失项和解除条件；不要用默认值补齐。
