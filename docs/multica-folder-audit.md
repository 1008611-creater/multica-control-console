# Multica 文件夹审计与改进执行提示词

审计时间：2026-09-27
审计范围：`E:\codex\multica` 的项目规范、产品文档、状态登记、验证入口、自动化测试、目录与版本控制边界。
审计方式：只读检查文件、目录大小、Git 状态；运行现有仓库验证和自动化测试。没有登录平台、提交任务、付费生成、下载媒体或清理目录。

## 结论

项目已经有可工作的本地抽卡控制台、安装/分发产物、规范检查和重试逻辑测试；主要问题不是缺更多流程文档，而是“产品到底是什么”和“哪些文件属于源码、运行数据、发布包”没有统一到一个权威定义。当前验证通过不能证明安装包在另一台机器可用，也不能证明浏览器界面完整可用。

不可能用一句提示词保证项目绝对变好；可行的做法是让提示词强制先拿证据、选高价值小步、实际修改、跑验证并检查用户能否使用，避免只产出计划或继续堆文档。

- [已验证] 当前 `git status` 同时有大量已修改文件、未跟踪目录和运行/分发内容；它不是干净工作区。本轮不能仅凭状态判断这些内容哪些是临时文件、哪些是用户要保留的交付物。

- [风险判断] 接手任务时可能依赖损坏或过时信息，造成重复操作或错误宣称当前状态。
- [改进方向] 先保留历史副本，再建立短小、可机器检查的“当前状态”与“历史事件”分层；不可恢复的乱码标为不可还原，不得猜写原文；为日期、唯一当前状态、下一步和历史归档建立轻量检查。

### P1：自动检查通过不等于产品交付链路通过

- [已验证] `npm test` 通过：12 项 Node 重试测试、3 项 Python 测试。
- [已验证] `npm run verify` 是文档、状态、路径、技能元数据和敏感字段模式检查。
- [已验证] `package.json` 中没有浏览器验收、安装包构建/清单检查或干净机器安装测试入口。项目记录中的 Playwright、临时安装和实际页面测试是曾经做过的单次验证，不是当前每次构建都会自动执行的门禁。
- [风险判断] 文档和核心重试逻辑有一定覆盖，但 UI 状态映射、安装/升级保留数据、发布目录内容与源码一致性容易回归。
- [改进方向] 先确定最小、稳定、无付费的自动验收：页面关键文字和按钮闸门、桥 API 样例状态、包内文件清单/敏感路径、临时目录安装启动停止、升级哨兵数据保留。只把稳定检查加入常规验证；跨机器和真实平台验证仍作为明确的人工验收项。

### P2：文档数量和历史重复已超过当前状态的可读性

- [已验证] 根目录同时有旧审计与阶段操作卡、新的生命周期和产品文档、桥运维文档、当前状态日志；`assistant/THREADS.md` 也保留多份重复验收记录。
- [风险判断] 继续添加总结文件会加重权威源不清。问题应通过归并入口和历史归档解决，而不是继续扩充说明文档。
- [改进方向] 定义“当前入口、真源状态、历史证据、可复制模板、运行/发布产物”五类；每类只设一个索引入口。保留审计追溯，但让普通使用者从一页开始。

## 优先顺序

1. **保护现场并确定唯一产品定位**：在动目录前记录 Git 状态；由用户当前方向确定本仓库主要交付是可分发抽卡工作台，治理文档作为它的工程支撑。
2. **收敛入口和当前状态**：修复 README、PROJECT_CONTEXT、product-spec、架构和状态登记的冲突；历史乱码不能猜修。
3. **划清源码与发布边界**：设计 `runtime/`、`dist/`、`installers/`、`.playwright-cli/` 的保留和忽略策略；先清单、后迁移，绝不直接删除用户数据。
4. **补最有价值的自动验收**：优先检查产品关键路径和分发包完整性，不要为了测试数量引入庞大测试平台。
5. **完成一次真实用户路径验收**：本机已安装版本启动、操作、停止及升级保留数据；另机安装要单独标记，不用本机样例冒充。
