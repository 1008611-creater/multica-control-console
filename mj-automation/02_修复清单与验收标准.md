## 断点 1（最关键）· 下载失败静默降级成缩略图，对外仍报成功

**原来**：`generate()` 里 `if (!images.length)` 就回退到 `downloadLatestImages()`，
后者抓页面缩略图 URL、不做任何校验，然后返回 `success: true`。
真实日志：`GEN success=true images=4`，而 4 个文件里 3 个是占位图/缩略图。

**改成了什么**：

- 删掉那条静默降级路径。
- `downloadLatestViaButton()` 的每一条子路径（下载按钮 / 灯箱 outputs / 预览器下载 / 详情页 DOM）
  落盘后都必须先过 `_verifyDownloads()`；**不合格就不算成功，继续往下一层兜底**。
- 所有路径都失败时返回 `{ ok: false, success: false, status: 'download_failed', rejected: [...] }`，
  并附一句 `warning`：图可能已生成在站内，请人工查看，别盲目重跑。
- 保留原有的防重复扣费设计：点过「立即生成」之后，任何超时都返回
  `receipt_pending` / `retry_allowed: false`，不自动重试。平台已判失败的终态返回 `page_reported_failed`。

**验收**：

- [ ] 跑一次真出图，成功时 `status == "ok"`，且 `files[].bytes` 在 5–10MB 量级
- [ ] 人为制造失败（例如生成中途断网）后，返回里 **不再出现 `success: true` + 小文件**
- [ ] `rejected` 数组能说清每个被拦文件的原因

## 断点 2 · 没有内容校验，垃圾被当成产物

**原来**：只判断「文件是否写成功」。140KB 的 loading GIF、1KB 的错误页都能通过。
讽刺的是 `dl_by_serial.js` 里**已经写好**了尺寸校验，只是没接进主流程。

**改成了什么**：新增独立模块 `scripts\verify_result.js`，作为**唯一判定入口**。
判定顺序：魔数 → 格式白名单 → 字节下限 → 尺寸下限。

| 判定码 | 含义 |
|---|---|
| `OK_HD` | 通过 |
| `PLACEHOLDER_GIF` | GIF 占位图（MJ 不产出 GIF） |
| `NOT_IMAGE` | 内容是 HTML/JSON 错误页 |
| `TOO_SMALL_BYTES` | 字节数不足 |
| `TOO_SMALL_DIM` | 尺寸不足 |
| `BAD_FORMAT` / `EMPTY` / `UNREADABLE` | 其他不合格 |

默认闸门：**≥200KB、≥1024×1024**，可用 `MJ_MIN_BYTES` / `MJ_MIN_DIM` 调整。

这个模块被接进了：`generate()` 的下载判定、`downloadLatestViaButton()` 的每条子路径、
`downloadLatestImages()` 的 URL 抓取通道、`_downloadFromDetailDom()`。
**任何写盘后的文件都要过它才算「拿到了图」。**

**验收**：

- [ ] 用历史垃圾文件做回放测试，全部被判不合格：
  `M03_1_1.png`(24310B) / `M03_1_2.png`(29088B) / `MJ_01_1.png`(18144B) /
  `MJ_01_2.png`(31522B) / `MJ_CS_1_2.png`(1161B) / `niannian_cine_1.gif`(140077B)
- [ ] 用历史高清文件做回放测试，全部通过：
  `M07_南天门_MJ8.2_v1.png`(9340180B, 1792×2688) / `M01_1_1.png`(7714807B, 1792×2688)
- [ ] 不合格文件在 URL 抓取通道里被**主动删除**，不留在 output 目录

## 断点 3 · 比例的「两个来源」互相打架（已修复）

**原判（已作废）**：以为中文版只有 1:1 / 1:2 / 3:4 / 3:2 四档，`9:16` 要映射成 `1:2`。

**实测真相（2026-09-12 页面探针）**：尺寸按钮是**八档** ——
`1:1 / 1:2 / 16:9 / 9:16 / 4:3 / 3:4 / 3:2 / 2:3`（按页面顺序），`9:16` / `16:9` **可直选，不需要任何映射表**。

**真正的问题（缺陷 J）**：比例有**两个来源** —— 界面档位 与 提示词正文里的 `--ar`。
两者会互相覆盖，于是出现「点了 9:16，出来却是 1:2」的错位，而日志照样打「已选择尺寸: 9:16」。

**改成了什么**（`scripts\mxai_adapter.js`）：

- 选档前先 `stripAspectParams()` 把正文里的 `--ar` / `--aspect` 剥离 → **界面档位成为唯一权威**
- 只在 `.mj-left-tool` / `.mj-theme-page` 范围内找尺寸按钮（宽<160、高<60、文本完全相等），不再模糊匹配
- 点完后**回读选中态**（class 含 selected/active/checked/primary 或 `aria-checked=true`）
- 回读不一致 → 抛 `ASPECT_NOT_APPLIED`，**在点「生成」之前抛出 → 不扣费**
- 新增 `allowAspectDegrade = false`（默认关闭）：宁可失败，也不悄悄降级画幅
- 返回 `{ ok, requested, applied, note }`，并记进 `this._lastAspect`；回执里 `requested_aspect` / `aspect` / `degraded` 三字段可对照

**验收**：

- [ ] 用 `--ar 9:16` 出一次图，回执 `requested_aspect="9:16"`、`aspect="9:16"`、`degraded=false`
- [ ] 产出的图片实际宽高比 ≈ 0.5625（9:16 竖图），而不是 0.5（1:2）或 1.0
- [ ] 用 `--ar 16:9` 出一次图，`aspect="16:9"`，产出是横图
- [ ] 故意让档位点不中，确认在**生成前**就报 `ASPECT_NOT_APPLIED`，且积分未被扣

## 缺陷 G / I · 点「下载」后 1.8 秒自毁（已修复）

**原来**：页面点「下载」拿到的是 Blob 链接，约 **1.8 秒后失效**；慢一步就只剩缩略图或 loading 占位图。

**改成了什么**：改走**直链快车道** —— 先按站内 serial 拼 CDN 直链直接下载，
规律为 `https://cdn.qihuiai.com/attachment/draw/outputs/100595791/<YYYYMMDD>/<serial>_0.webp?auth_key=...`，
绕开那个短命 Blob。配套的尺寸/字节/魔数校验由 `verify_result.js` 统一把关。

**注意**：CDN 直链返回的是 **WebP**（实测 1536×3072），站点 Blob 返回的是 **PNG**（实测 1536×3072）。
两者像素一致，按需取用；`mj_run.js` 已按 `info.format` 决定归档扩展名。

## 断点 4 · 记账入口与实际出图入口割裂

**原来**：会记账的只有 `server.js` 的 REST/MCP 入口（`appendMxaiReceipt()`），
而实际在用的 CLI 脚本完全不写账 —— 所以 `mxai-tasks.jsonl` 是 **0 字节**，
同期却躺着 27 个产物。出了图没有账，既算不出成本也复盘不了。

**改成了什么**：新增 `_writeReceipt()`，**挂在 `generate()` 内部**，
不管走 HTTP、MCP 还是 CLI，只要经过 `generate()` 就一定写账。
落点由 `MJ_RECEIPTS_DIR` 控制，默认 `mj-automation\receipts\`（不污染原目录）。
成功、失败都写，字段含 `task_id / prompt_hash / serial / aspect / files[] / rejected[] / status / seconds`。

**验收**：

- [ ] 跑一次真出图后，`receipts\mxai-tasks.jsonl` 有且只有一行，字段完整
- [ ] 故意跑一次空提示词，确认**没有**产生回执（在 `generate()` 之前就被拦了）
- [ ] `GET /v1/receipts?tail=20` 能读到同样内容

## 断点 6 · 安全执行器硬阻断 image 批次

**原来**：`ai-rpa-console\server.js` 的 `executeBatch()`（177–198 行）对非 `file`、
非 `browser.read_only` 的任务直接返回 `blocked`，文案「安全执行器仅允许 file 或 browser.read_only」。
`app.js` 的 `isSafeReadOnlyBatch()` 同源。

**这不是 bug，是刻意设计的合规闸门。** 但副作用是：一旦把出图任务接进 Multica 批次协议，会被硬拦。

**改成了什么**：**不动那个闸门**。改为在闸门之外另开一条授权通道：

- 出图走 `scripts\server.py`（FastAPI），不经过 `ai-rpa-console\server.js` 的批次执行器。
- 付费动作按**批次授权**：每批只问一次，用户确认后才批量提交。
- 服务本身不做任何自动重试；`receipt_pending` / `page_reported_failed` / `download_failed` 一律交人工判断。
- 自动补下载只认 `queued` / `download_failed`；`receipt_pending` 与 `page_reported_failed` 都不再是候选。

**验收**：

- [ ] `ai-rpa-console\server.js` 原文件**未被修改**（保持闸门原样）
- [ ] 出图请求全部走 `127.0.0.1:8765`，日志里不出现 `blocked`
- [ ] 每批出图前，用户明确确认过一次（有记录可查）
