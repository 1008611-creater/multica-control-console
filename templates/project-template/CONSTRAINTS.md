# <项目名> 质量与安全约束

## C1 · 真实性

- 只记录用户提供或仓库中可以回溯的真实数据。
- 缺失字段统一写「缺」，不得用 0、估算值或主观判断填充。
- 不把样例、预览图或历史界面截图当作真实效果证明。

## C2 · 权限与合规

- 不代替用户登录、发送或发布任何内容。
- 对外动作由用户本人完成，并以对方最终成功回执为准。
- 付费操作按批次授权；每批次只询问一次，用户保留最终确认权。
- 不读取、写入、迁移或输出 Cookie、Token、API 密钥、密码、证书、`.env`、`.pem`。

## C3 · 架构边界

- 目录职责在 `docs/architecture.md` 中定义，新增目录必须先登记。
- 外部系统的数据保持只读引用，不复制真源。
- 自动化只能派发任务，不能替代人工确认或授权。

## C4 · 可验证性

- 每个可交付阶段必须有明确完成条件和验证命令。
- L0 文档变更：结构检查即可。
- L1 单模块逻辑：结构检查 + 定向测试。
- L2 跨模块或接口：契约检查 + 复核 + 文档同步。
- L3 权限、数据、部署或架构变化：安全审计、回滚方案、运行验证和审计记录。

## C5 · 变更风险

| 等级 | 范围 | 最低要求 |
|---|---|---|
| L0 | 文案、模板、纯索引 | `npm run verify` |
| L1 | 单个模块 | 定向验证 + 一次复核 |
| L2 | 跨模块、状态模型、任务接口 | 契约检查 + 文档同步 + 回归验证 |
| L3 | 凭据、权限、数据、部署、架构边界 | 安全审计 + 回滚方案 + 运行验证 + 审计记录 |

## C6 · 交付格式

每个交付必须说明：目标、事实依据、修改范围、验证命令与结果、风险和用户下一步动作。未发布内容必须明确标注为草稿。
