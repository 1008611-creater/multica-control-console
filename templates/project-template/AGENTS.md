# <项目名> 工程约束

## 项目定位

用一句话写清这个仓库负责什么、不负责什么。边界越具体，后续越少返工。

示例：本仓库负责 <职责范围>，不负责 <明确排除项>。

## 任务生命周期

所有中大型变更按以下顺序推进：

```text
DEFINE -> PLAN -> BUILD -> VERIFY -> REVIEW -> SHIP -> RETRO
```

每个阶段都必须有输入、产物、责任人和进入下一阶段的条件。没有验收证据不得标记完成。

## 架构边界

```text
任务入口
  -> docs 与约束
  -> scripts 验证
  -> 资产与索引
  -> 外部执行现场（只引用，不接管）
```

- 根目录规范文件定义跨模块规则；`docs/` 定义本仓库目标、设计和验收。
- `scripts/` 只做检查与自动化，不承载业务判断。
- 原始生产目录或外部系统保持只读引用。
- 不得把界面操作、平台登录、发布动作塞进脚本或自动化任务。

## 变更规则

- 先读 `PROJECT_CONTEXT.md`、`CONSTRAINTS.md` 和相关 `docs/` 文件，再修改实现。
- 每个任务尽量控制在 2-5 个文件，并说明输入、输出和验证命令。
- 架构、约束、状态模型变化必须同步更新文档和 ADR。
- 只使用真实可核验的数据；未知字段写「缺」，不得估算。
- 任何付费、登录、发布或对外发送动作都需要用户当次明确授权。
- 不提交 Cookie、Token、API 密钥、密码、证书、`.env` 或本地运行时日志。

## 验证

提交前运行：

```powershell
npm run verify
```

该命令至少检查规范文件完整性（含 `docs/lifecycle.md`、`docs/release-checklist.md`、`docs/retro-template.md`）、敏感信息模式、Markdown 基本结构、相对链接完整性和脚本编码。验证失败时不得声称完成。
